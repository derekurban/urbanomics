# Claude suggestions

November 21, 2026. Urbanomics can use Claude, through the person's own Anthropic API key, to suggest how to organize the workspace. Four features: Suggest missing tags, Suggest a restructure, Suggest aliases, and Smart organizing on the Organize desk. Claude never changes anything itself: every suggestion is applied by the app through the same versioned APIs as a manual change, after the person approves it or, with Apply automatically on, as it arrives.

This replaces the Codex CLI bridge of October 4, 2026 (a ChatGPT subscription through `codex exec`). The prompts, validators, reviews and the Organize batch are the same; only how the model is reached changed. A Codex run carried 15–20 thousand tokens of the CLI's own instructions and took five to six seconds for one transaction; a direct request is about 1,700 tokens and under two seconds.

## Connecting (Settings → Assistant)

- **API key.** The person pastes a key from the Anthropic Console. It is checked with Anthropic (by listing models) before it is kept; a refused key is reported and dropped. The desktop app stores it encrypted by the operating system (Electron `safeStorage`: DPAPI on Windows, the Keychain on macOS) in the private workspace `settings` table (`assistantKey`). A host without that (the browser host) holds a key only until it closes. `ANTHROPIC_API_KEY` in the environment is the fallback when no key is saved. The key is never returned to the page (only its last four characters), never logged and not part of the configuration export; Start from scratch clears it. Replace and Remove are in the same block.
- **What Claude can read.** A consent checkbox must be on before any feature runs. It states what is sent: descriptions, amounts, dates, account names, tags, people and events, to Anthropic under the person's key, only while a feature runs.
- **Features.** Each feature has its own model and reasoning level, chosen from the models the key can use (`models.list`, those that support structured output, with the reasoning levels each supports). Smart organizing defaults to Haiku 5.5 at medium; the three one-off reviews default to Opus 5.5 at the model's default. A choice saved for another provider's model falls back to the default. Smart organizing has an on/off switch, here and in the Organize heading. Settings live in the private `settings` table (`assistant` key).

Remote phone access cannot save or remove the key (the web host refuses those calls when it serves the desktop); suggestions themselves work from any host. The old address `#settings/codex` opens this section.

## How a request works

`electron/ai/claude.cjs` sends one Messages API request per answer with `@anthropic-ai/sdk`: the prompt as the only user message, `output_config.format` set to the feature's JSON schema, and `output_config.effort` when a reasoning level is chosen. There are no tools and no files, so Claude sees only the prompt and must answer in the schema. Sonnet 5.5, Opus 5 and 5.5 and the Fable models also send `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`), so a request one model declines is retried on another inside the same call. The SDK retries rate limits and server errors twice; a request times out after four minutes. At most `organizeSlots` requests run at once (1–32).

Failures are worded for the person and the Organize batch matches that wording: an invalid key, a model the key cannot use, a rate limit (429), a busy service (5xx), a timeout, no network, and an empty credit balance. Every request leaves a line in the private `logs/assistant.log`: model, time and token counts, or the failure reason; never the prompt, the answer or the key.

`electron/ai/prompts.mjs` builds each prompt and validates each answer. Validators keep only what points at real things (existing ids, offered candidates, names that don't already exist), fix what can be fixed (cents that must add up, a "new" category that already exists) and drop the rest. The Other fallback tag is never offered.

## Model and settings: what was measured

November 21, 2026, 43 labelled invented transactions (history-backed, cold, unknowable, transfers, traps, people, events, new tags) through the real prompts and validators, two to six runs per configuration. "Wrong" is a confident suggestion Apply automatically would have written incorrectly; holding back is safe.

| Model, reasoning | Correct | Wrong | One row | Ten rows per request | Cost per 1,000 rows |
|---|---|---|---|---|---|
| Haiku 5.5, low | 93–98% | 1 in 258 | 1.5 s | 4–9 s | $0.11–0.26 |
| Haiku 5.5, medium | 98% | 0 in 258 | 1.8 s | 9–11 s | $0.16–0.30 |
| Haiku 5.5, thinking off | 88–98% | 2 in 129 | 1.3 s | 5–6 s | $0.09–0.24 |
| Sonnet 5.5, low | 98–100% | 0 in 387 | 1.9 s | 5–6 s | $1.70–4.70 |
| Opus 5.5, low | 100% | 0 | 2.1 s | 8 s | $3.40–9.30 |
| Fable 5.2, low | 100% | 0 | not run | 9 s | $6.80 |

Haiku 5.5 at medium is the default: no wrong writes, under two seconds a row, about nine cents for a 300-row backlog. Sonnet 5.5 at low is the accuracy option. The set is small and the three larger models all reach its ceiling, so it does not rank them against each other. Thinking is left on: with it off, Haiku twice read a paycheque as a friend settling up.

Three hundred and one rows on Haiku 5.5 at medium, by requests at once × rows per request: 16 × 1 took 44 s and found 27 of 28 events and shares; 16 × 5 took 31 s and found 19; 16 × 10 took 30 s and found 15; 32 at once was faster still but ran into rate limits on a new key. So the defaults are 16 requests at once and one transaction per request: larger requests cost about half as much and save little time, and they miss more events and shared expenses.

## The features

- **Suggest missing tags** (Settings → Categories & tags → Suggest). Claude sees the categories and tags with usage counts and up to 250 transaction names (untagged first) with direction, count, total and current tags. It proposes up to 12 new tags, each with an existing category, a new category or none, a reason and the names it fits. The review lets you uncheck, rename and recategorize each, and offers to tag the matching transactions that have nothing on them yet (only rows with no tags, repayment or transfer). Approving creates the categories, then the tags, then tags those rows with the whole amount through `organize`.
- **Suggest a restructure** (same menu). Claude sees the structure with usage, rules and example names per tag. Changes are create-category, create-tag, rename, move, merge and delete. With fewer than three tags (a new workspace, or after Start from scratch) the prompt asks for a complete starting structure of 4 to 8 categories and their tags, and lists the transactions so each new tag carries the names it fits; the review offers to tag the untagged ones, as Suggest missing tags does. The empty Categories & tags page offers "Suggest a structure from my transactions". Transfers, card payments and e-transfers with friends are never made into tags, in either feature. Each tag takes one change (a merged tag takes no other); deletes are limited to unused tags that are not merge targets and categories the plan empties; a move into a new category, or a category delete, is tied to the changes it needs. Approved changes apply in order (create, rename, move, merge, delete) and each reports its outcome. Merge is a server operation, `review:merge-tags`: one transaction moves every portion (bank and cash, archived accounts too) and every vendor that gives the source tag over to the other, summing portions on rows that had both, deletes the source tag and writes a private recovery copy under `backups/admin`.
- **Suggest vendors** (Vendors → Suggest vendors; the feature's stored key is still `aliases`). Claude sees up to 400 descriptions without a vendor, with counts, and the existing vendors with their matchers. Each suggestion is a name plus one or more plain matchers (starts with, contains, ends with, is exactly) that compile as the vendor editor's do. The server previews each with the vendor store's own check; ones that match nothing are dropped and clashes are shown. Editing a name or matcher re-runs the preview. Approved vendors save one by one through `saveVendor`, which still refuses overlaps; tags and people are set afterwards in the vendor editor.
- **Smart organizing** (Organize). With the switch on, opening an unsorted row asks Claude about it and prefetches the next unsorted row. The context is what the describe box already offers for that row: tags for its direction, people (with what they owe on money in), the 30 events nearest its date, likely transfer twins, expense categories, and up to 25 earlier rows with the same name or a similar description and how they were organized. Claude can suggest tags with amounts, one new tag when nothing fits, a twin, a person settling up, people to share with, a payee and an event. The card shows each with its reason and a checkbox (low-confidence ones start unchecked) and Apply. Applying uses the desk's own gestures in an order that keeps cents adding up: a twin alone (plus an event), otherwise settling first, then tags and the event in one save, then the split, then the payee; a new tag is created first. The flow then moves to the next unsorted row as a manual tag would, and Undo works as usual. Answers are remembered for the session by what was asked. Sorted rows offer "Ask Claude what this is" instead of asking on open.
- **Suggest for all unsorted** (Organize, in the Claude menu). Asks Claude about every unsorted row, newest first, through a pool of slots: Settings → Assistant sets how many requests go at once (1–32, default 16) and how many transactions each request takes (1–10, default 1; `ai:suggest-organize-batch`, `organizeBatchPrompt` for more than one, each row with its own candidates and validated on its own). A slot that finishes takes the next rows from the queue at once. Each row's context is built from the ledger as it is at that moment, and a row sorted meanwhile, or the other half of a transfer this run just linked (both halves are claimed when a twin is applied), is skipped rather than asked or linked twice. When Anthropic turns requests away (a rate limit, a busy service, a timeout, no network), those rows go back to the front of the queue, the pool halves the requests it keeps going and pauses 2 s, doubling to 30 s, then adds requests back as answers come in cleanly; several refusals inside one pause count once; a row gets three tries. A row the model skips is retried once at the back of the queue. An empty credit balance stops the run and says how many rows were not reached; an invalid key, a missing consent or an unavailable model stops it with the reason. Every row ends in exactly one outcome (organized or ready for review, waiting for review, nothing to suggest, already sorted or linked, failed), the heading shows "Organizing N of M · K applied" with how many are with Claude now (and "Claude is busy, retrying in N s" while paused), and the closing toast lists the counts, which add up to the total; a row Claude organized that still has an unsorted part (for example only "Paid Priya") is called out, and a row whose suggestion is fully applied no longer keeps a green star, so the Unsorted and Suggested chips match the summary. It works with the Smart organizing switch off. While Claude is connected and suggestions are in use, each unsorted row carries a star in the shape column: a grey outline when there is no suggestion (not asked yet, nothing to suggest, dismissed or failed, with the reason on hover), a pulsing star while Claude is asking, and a filled accent star when a suggestion is waiting. Sorted rows have none. A Suggested filter (with a count) lists the rows with a waiting suggestion; when the run ends, a toast offers to show them. Opening a starred row shows its suggestion; Apply (or Enter in the empty describe box) moves to the next suggested row as the flow does (skipping a twin it just linked). A closed row draws its waiting suggestion in the strip as a dashed outline, and `a` accepts the focused row's suggestion. The suggestions and a running batch belong to the app session (`src/organize-store.js`), so they survive leaving Organize; only one batch runs at a time. The batch uses the Smart organizing model and reasoning level.
- **Apply automatically** (a switch in the Organize Claude menu and under Smart organizing in Settings → Assistant, stored as `autoApply`). The button becomes Organize all unsorted: each answer is applied as it lands, without review, through the same gestures as Apply (success toasts are held until the run ends; errors still show). The row you open with Smart organizing on is applied too, without moving on. Since November 21, 2026 (after a 163-row run split six restaurant meals with a friend, recorded a settlement and created both "Interest" and "Interest income"), only what amount, date and history can support is applied without review: tags you already have that are not low confidence, a transfer twin that is high confidence and mutually unique under the saved matcher settings (the row has exactly one candidate and that candidate has exactly one, this row), and an event with no participants. Shares, settlements, "Paid <person>", new tags, events with participants, any other twin and anything low confidence wait with the row's star filled; a row can be partly applied (its tag) with the rest waiting, and the closing toast says on how many rows Claude has more to review. The rule is `splitForAutoApply` in `src/organize-rules.mjs`, tested in `tests/desktop/organize-rules.test.cjs`. An Auto-applied filter lists every row Claude organized this session, and each change can be undone as usual.

## Verification

- `node --test tests/desktop/assistant.test.cjs`: validators for all four features, the tag merge (portions, vendors, recovery copy, versions), settings and consent, the key (checked before it is kept, stored only encrypted, never returned), how a request is built and how failures are worded, organize caching and batching. No network calls.
- `ANTHROPIC_API_KEY=… node scripts/smoke-assistant.cjs [--model claude-sonnet-5-5] [--only …]`: the real app against an isolated synthetic workspace (`scripts/assistant-demo-data.cjs`) and the real API. It enters a refused key and then the real one in Settings, runs Smart organizing on six rows (groceries, a savings transfer, a friend settling up, fuel during an event, a new pet tag, an e-transfer to a friend), then approves missing tags, a restructure and vendors, checking the workspace after each, runs Suggest for all unsorted and applies three suggested rows in a row, then, on fresh workspaces, Organize all unsorted over 313 rows with Apply automatically on and a restructure from no structure at all. It records one video per feature under `private/validation/assistant-<time>/videos`. It costs a few cents and sends only invented data.

## Known limits

- Suggestions are only as good as the model and the history; the reviews exist because they can be wrong. Validators guarantee that applied changes are valid, not that they are wise.
- Only Anthropic is wired up. `claude.cjs` is the one place that talks to a provider (`check`, `listModels`, `exec`), so another provider would be a second module of that shape.
- In a browser (the browser host, or the phone), a page can hold only about six connections to the app at once, so fewer requests run together there than the setting says. The desktop app talks to its main process directly and has no such cap.
- Every applied row still reloads the ledger, so on Organize all unsorted the app's own saving, not Claude, sets the pace once the ledger is a few thousand rows.
- A key on a new Anthropic account has low rate limits; the batch slows itself down rather than failing, but 32 requests at once only helps on higher tiers.
- Claude suggests vendors' names and matchers, not the tag or person a vendor gives new transactions.
