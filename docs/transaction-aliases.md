# Transaction aliases

Organize → Aliases manages readable transaction names separately from imported source data. The account-alias shortcut opens Organize → Accounts, which retains account names, filename-prefix regexes, filename tests and routing safeguards.

A transaction rule has a readable name (1–80 characters), a description regex (1–256 characters), and an optional account scope. Rules search original bank descriptions case-insensitively using the existing RE2 engine. They do not match alias output, chain aliases, infer people, or classify transactions. Use `^` and `$` for anchoring. Lookarounds and backreferences are unsupported. Names are literal replacements, not capture-group templates.

The editor's **Without an alias** panel lists transactions with no matching rule, independently of their categories or financial-review status. It covers all months (including labeled deleted accounts), follows the selected account scope, and supports searching bank text/account/date and paging ten rows at a time. Conflicting transactions stay in the conflict list instead. Clicking a row seeds an escaped, anchored exact-description regex and focuses the readable name. Regex punctuation is treated literally; descriptions that exceed the rule length limit require a shorter manual pattern rather than silent truncation.

**Save & create another** saves through the same conflict checks, keeps the editor open, clears the name/pattern and old preview, and refreshes the remaining transactions. All rows covered by the saved rule leave the panel. Account scope and search remain available for continuing the batch. Normal Save closes the editor; Cancel never saves a draft.

Test against transactions previews all imported ledger rows, across months and including deleted accounts. Each match shows original text, proposed name, account, date, amount and any competing aliases/patterns. Results are searchable and paginated in groups of 25. Every match participates in conflict detection, including matches outside the visible page. Editing a rule excludes its own previous definition from comparison. Changing the draft invalidates its preview.

Save requires a successful current preview in the UI. The main process revalidates the rule and rescans matches inside the save transaction. Overlapping matches and duplicate names or exact patterns in overlapping account scopes block saving. Disjoint account scopes may use the same name/pattern. A rule with zero current matches can be saved for future imports. Versions reject stale edits/deletions. Deleting a rule restores original names or another uniquely matching alias without modifying financial decisions.

The preview detects overlap on existing transactions; it does **not** prove arbitrary regexes disjoint for every possible future string. Every displayed transaction is checked against the current rules. Exactly one match applies its alias. Multiple matches keep the original name and expose the competing rule IDs; Organize shows those rows with actions to edit each competing rule. Refining or deleting a rule resolves the ambiguity immediately. No rule wins by order or priority.

Schema 7 adds `transaction_aliases` in private SQLite. No existing data is rewritten during migration. Aliases decorate Review records and the current Transactions IPC response. Search finds original descriptions and aliases; the card tooltip, transaction settings and financial review retain access to original descriptions. Source inspection and immutable snapshots always show original imported text. `ImportStore.transactions()` remains raw because it also supplies snapshot generation. Aliases never affect fingerprinting, repeat detection, ledger identity, financial review versions, categories, event membership or repayment links.

The alias store reuses compiled expressions for each normalized pattern during its lifetime. Repeated previews and refreshes therefore avoid recompiling every saved rule into RE2's fixed memory heap. A synthetic 100-rule regression exercises repeated previews and state reads alongside the existing conflict checks.

`npm test` checks all-month/deleted-account previews, exact and overlapping rules, unsupported regex syntax, account scope, stale writes, raw-data preservation, future ambiguity, rename/delete and restart. `npm run test:aliases` exercises the real Electron editor, preview invalidation, conflict blocking and resolution, current-rule rechecks, aliases in Review and Transactions, original-text access, the account shortcut, narrow/focused layout and persistence. Only synthetic imports are mutated in tests.
