# Working on Urbanomics

Read `README.md` and `docs/direction.md` before implementation. Keep user statements, proposals, and verified behavior distinct. The earlier conversation is background, not authority to copy its architecture.

## Project boundaries

- Build from scratch. The accepted first workflow now uses Electron + React (Vite) with SQLite owned by the main process. Read `docs/desktop-imports.md` before changing ingestion or persistence.
- Start with a small, runnable experience using synthetic data, then extend it based on the user's reaction.
- The user has accepted the sixth trial's overall flow and playful sorting experience as the implementation direction. Preserve it while building real import and persistence; visual cleanup and animation can follow. Individual accounting defaults still need validation.
- The accepted Data layout unifies Dropbox intake, upload history, archived originals and an account-by-month snapshot map. Recognized uploads with a resolved account process automatically. Files discovered by startup/focus/Refresh remain staged until Process. Account version counts must exclude saves that changed only another account. Keep real folder actions and cleanup confined to app-owned intake copies.
- The Snapshots page (formerly Data) stays compact with Refresh in an overlay snackbar, a rolling 12-month calendar ending at the later of the latest imported month and last completed month and processing results in a playful modal. Show only one current snapshot per account/month; older immutable saves remain audit files. Archive account rows stay expanded and original uploads are collapsed. Dialogs scroll inside an inset frame. Account-colored squares show snapshot presence without revision labels; history and archive inspection use modals. Accounts have editable names, colors and tested filename-prefix regex rules. Conflicting matches require review.
- Keep this file and discovery notes current when the user settles a decision.
- Imports use each bank-exported transaction date without a month or range selector, including current-month rows. Exact fingerprints match existing same-account transactions one-for-one, retaining incoming duplicate multiplicity and stable IDs/reviews. Additional rows append to their monthly snapshot; partial exports never delete existing rows. Re-uploading an old filtered original fills its excluded rows; startup does not backfill archives. Ambiguous account routing still requires assignment. Staged matches can explicitly be kept as additional payments.
- Review → Transfers shows pending incoming transactions on the left and same-currency outgoing candidates in other accounts on the right, across imported months. The adjustable symmetric percentage band is relative to the outgoing amount (default 2%, precision 0.01%). Explicitly selecting both and pressing Link pairs them atomically and advances; Linked provides history/filtering and Unlink. A shortfall defaults to a fee once, on the outgoing review; extra received stays an unexplained difference on the incoming review. Preserve raw records, categories and events. Reject stale pairs and entries reserved by repayments; unrelated completed financial reviews must be reopened first.
- Upload history leads with the account and color; source files and receipt details expand below compact rows. Account deletion is recoverable: remove it from active views/routing, preserve local ledger/archive/history, and offer Restore. Pending uploads return to assignment; finalizing imports must finish recovery first. Never delete real accounts as part of UI verification.
- Do not delegate to other agents unless the user explicitly requests it.
- Organize manages Categories, Events, Accounts and People. Categories directly own transaction portions; the separate tags and category-view model is superseded. Use the shared EntityEditor in Organize and Review. Preserve routing, remembered filenames and recoverable deletion under Organize → Accounts.
- Category review uses cards; do not reintroduce the board. Dropping onto a category (or pressing its target button) saves 100% to that category and advances to the next unfinished card only after success. Clicking the card opens Transaction settings with searchable multiple categories and exact-cent split controls. Save persists and advances; Cancel, Escape and backdrop dismissal leave both data and the current card unchanged. Failed saves keep the modal open. Save/Cancel remain visible outside its scroll area.
- Clicking an already selected category or its selected chip removes that category, redistributes its portion among remaining categories, saves, and stays on the current card. Removing the last category makes it pending again. Dropping still assigns the full amount and advances. Chevron icons are centered in square controls at every layout size.
- Organize → Aliases manages readable transaction names with global RE2 description regexes across every account, plus a shortcut to the existing account name/prefix settings. Preview all ledger transactions (all months, including deleted accounts); block overlapping existing matches, duplicate names/patterns, and stale saves. Recheck at save time. Future ambiguous matches retain the original description and appear in the conflict list. Aliases change display names only: preserve source descriptions, IDs, immutable snapshots, deduplication fingerprints and financial decisions. Read `docs/transaction-aliases.md` for behavior and limits.
- Aliases use compact rows for rule management, unmatched transactions and match previews; retain readable names, regex access, account/date context and amounts.
- Alias creation includes a searchable, paginated Without an alias panel, across all accounts and independent of category/review status. Exclude transactions already matched or in alias conflict. Clicking a row seeds an escaped description-prefix regex beginning with `^` and without a trailing `$`; do not truncate long patterns. Save & create another keeps the editor open, resets the new rule, and refreshes the remaining list after success. Existing preview/conflict checks still apply.
- Event review uses a calendar, with explicit per-transaction or per-day linking/unlinking to the selected event; membership is optional and never a completion queue. New and edited events require both start/end calendar dates with a default ±1-day suggestion buffer. Legacy undated events remain intact and show Dates required until edited; never invent dates. Bank dates remain unchanged, including their original timezone ambiguity. Events contain whole transactions independently of category portions and repayments. Costs & repayments shows gross paid, repaid, still fronted, agreed share and friends still owed, with unknown splits identified and currencies separate. Incoming event members can open repayment allocation; event selection resolves to unique expense IDs and later event changes cannot rewrite payment allocations. Financial review remains a separate inbox with people/shares, explicit repayments and paired own-account transfers. Read `docs/desktop-review.md` before changing it. Never classify real rows for testing.
- Schema 6 converts former tag entities to categories, preserving IDs and review payloads. The historical `review.tags` key now stores direct category portions for compatibility. Former category-view names remain available, with their old definitions preserved in private `review_entity_history`; they do not implicitly copy money from their former member tags. Import snapshots remain immutable. Gross category reporting must not infer net deductions or sender identities.

## Configuration and personal financial data

The app mirrors configuration changes into a deterministic SQL file, with explicit table/column allowlists. New empty workspaces seed from this file; existing workspaces retain their live configuration. Do not import SQL over an existing ledger. An explicit `URBANOMICS_CONFIG_DIR` connects the packaged app to the repository; isolated custom data workspaces export only when that path is also specified. The app writes SQL but does not run Git commits or pushes. Schema 8 clears legacy alias scopes and increments changed rule versions; ambiguous matches remain visible without changing financial decisions.

- Track code, documentation, schemas, synthetic fixtures, and the user-authorized account/alias/category/event/person definitions in `configuration/workspace.sql`.
- Keep actual imports, balances, transaction identities, links, splits, financial reviews, snapshots, archives, receipts, backups and runtime SQLite under `private/`, outside Git. Configuration entity identities/names, account filename rules and alias regexes are explicitly approved for Git as of 2026-09-11.
- Inspect staged files before commits. Ignore rules do not protect files already tracked or stored in unexpected paths.
- Do not transmit financial files to external services without the user's authorization.
- Coding agents may edit application code, synthetic fixtures, and the approved configuration SQL. Any future finance assistant should propose changes to private financial records through a reviewable application workflow.

## Correctness requirements for future implementation

- Use integer minor units or exact decimals for money; preserve currency.
- Preserve immutable source files and provenance.
- Never silently remove legitimate duplicate-looking transactions.
- A repeat import must not double-count; a partial replacement must not silently erase previously accepted transactions or break their links.
- Amount and date can identify candidates, but cannot prove a person's identity or a payment's purpose. Surface ambiguous matches for review.
- Show cash movement, the user's economic share, and unpaid reimbursements separately.
- Internal transfers and credit-card payments must not count as new spending or earned income.
- Label incomplete coverage and unresolved classifications; do not present uncertain totals as settled.
- Test these requirements with realistic synthetic edge cases when their implementation is added.

- Review → Money in makes income and expense deductions directly visible across all months. Income needs a type (paycheck, interest, sale, gift, or a named other source). Deduct expenses selects one or many unique expenses with optional event shortcuts. Expense review exposes Apply incoming money. Preserve excess separately from repayments and all source amounts.
- Manual CAD cash receipts live in private `cash_receipts`, not bank transactions/accounts or snapshots/configuration. They share the repayment capacity checks and can be edited or explicitly removed (voided with original receipt retained privately). Voiding releases deductions; stale edits and edits below allocated amounts are rejected. Never suggest manual cash as a bank-transfer counterpart. Schema 10 adds this table without changing any existing financial decision.

- Category review renders every category around one expanding ring, without target pages. Grow the ring within the window width and vertically as needed; preserve non-overlapping targets, searchable filtering, exact saved splits and card navigation. Edge scrolling keeps distant targets reachable while dragging.
